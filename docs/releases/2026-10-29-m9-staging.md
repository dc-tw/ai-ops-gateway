## 可重跑入口

```bash
sh scripts/test_m9_staging_stack.sh
sh scripts/test_postgres_pitr.sh
```

第一個腳本預設將 JSON 證據寫到 `/tmp/ai-ops-m9-report-<PID>`，以 PID 命名 Docker project，
並在結束時移除自己的 container、network 與 volume。設定 `KEEP_STACK=1` 才保留現場；可用
`M9_REPORT_DIR` 指定報告位置。第二個腳本同樣使用 PID 命名的獨立資源並永遠清理，不應指向
既有 PostgreSQL volume。

## 固定負載與故障結果

環境是單台本機 Docker／Colima、synthetic provider；下列數字只供相同環境回歸比較，
**不是 production SLA**。

| 階段 | 結果 |
| --- | --- |
| 1 併發／8 筆 | 0 error；p50 2008.25 ms；p95 2182.49 ms；max 2182.49 ms |
| 4 併發／8 筆 | 0 error；p50 4098.91 ms；p95 4315.77 ms；max 4315.77 ms |
| 16 併發／32 筆 | 0 error；p50 15047.44 ms；p95 21423.00 ms；max 26268.76 ms |
| 終止一個 Gateway 後 | 剩餘 1 replica，4 併發 0 error；p95 4410.11 ms |
| Gateway 恢復 2 replicas | 4 併發 0 error；p95 4833.25 ms |
| Redis 中斷／恢復 | 兩個 Gateway readiness 都回 503；恢復後都回 200；容器重啟 wall time 7 秒 |
| PostgreSQL 中斷 | 4 併發 8 筆仍 0 error；outbox lag 152、pending 24，未降級執行權威 |
| PostgreSQL／projector 恢復 | lag 0、pending 0；整段容器恢復 wall time 9 秒 |

負載快照中每個 Gateway 約 193 MiB、每個 Worker 約 122 MiB、每個 Scheduler 約 122 MiB、
每個 projector 約 46.6 MiB、Redis 約 12 MiB、PostgreSQL 約 53 MiB。這是單次 no-stream
觀察，不是容量上限或長時間 soak 結果。

初次以正式預設 `ATR_SCAN_TIMEOUT_SECONDS=5` 跑 16 併發時，32 筆中有一筆因掃描逾時而
正確 fail-closed（503 `atr_scan_incomplete`）；後續也確認預設 4 個 scan process slots 可能讓
請求在容量等待階段用完總預算。為了讓固定 staging workload 測量服務容量而非 scan budget，
只有 disposable overlay 將 timeout 設為 15 秒並配置 16 個 slots；production 預設沒有更動。
正式部署應依受控流量、host 資源與安全需求決定 scan budget，而不是直接複製本機數值。
