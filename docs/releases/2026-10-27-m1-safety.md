# M1：完整 ATR 掃描與安全決策持久化

狀態：M1 實作及本機／Docker 回歸完成。完整後續範圍見[交付追蹤](../implementation-roadmap.md)。
本紀錄只涵蓋 M1，不代表 M2–M9 已交付。

## 行為變更

- `ATR_ENABLED=true` 時不再截斷掃描。掃描 content、fields、metadata 的不同文字值合計
  超過 `ATR_MAX_CONTENT_CHARS` 即拒絕，不將未檢查內容送入下一個信任邊界。
- 完整掃描的命中仍依原有 detection-only／blocking、severity 及 allow/exclude 政策處理。
  **掃描不完整則兩種模式都拒絕**，不是把服務故障宣稱為攻擊命中。
- HTTP admission：容量超限回 413、無效文字回 422、掃描逾時／執行失敗回 503，
  `error=atr_scan_incomplete`；完整掃描後的規則阻擋仍回 403。錯誤不回顯內容。
- 事件保留舊 `truncated` 欄位（現在為 false），新增 `scan_complete`／`scan_reason`。
  無命中的完整決策 status 為 `passed`，不製造假的 finding。
- 所有啟用 ATR 的模型輸出都先緩衝、完整檢查後才釋出 draft token；buffer 上限是
  掃描上限加一字元，超限即中止上游 iterator。觀察模式也不再提前送出未掃描 token。

## 掃描程序與規則健全性

- regex 只在可拋棄的 spawn 子程序執行；父程序監督 deadline、取消及併發容量，
  逾時先 terminate，再必要時 kill，且關閉 IPC 與回收程序。
- 新設定：`ATR_SCAN_TIMEOUT_SECONDS=5`、`ATR_SCAN_MAX_WORKERS=4`、
  `ATR_SCAN_MEMORY_MB=512`。子程序也有 CPU／wall deadline；Linux 額外限制 address space，
  macOS 不宣稱具有相同的記憶體限制。限制為每個 Gateway／worker 程序，不是租戶總額度。
- 固定 `pyatr==0.3.1`，本地規則 revision 為 `gateway-atr-0.3.1-r1`。
  `ATR-2026-00290` condition 3 的 `\\1` 原本沒有 capture，僅將外層 non-capturing group
  改為 capturing group；不是移除 condition，也不是宣稱上游已修復。
- 規則逐條嚴格載入；無法解析的規則、自訂目錄中的壞檔、重複 ID、未知 operator／logic
  或必要 regex compile failure 都拒絕啟動，不把非零規則數當健全性證明。
- `/healthz` 額外揭露規則內容 fingerprint 與是否要求完整掃描，不公開規則本文。
  規則修正不代表可自動升級為 blocking；合成語料結果也不能推論正式誤報率。

## Journal 與恢復

- graph 在 tool args、tool response、model output 的掃描完成後，先同步提交 Redis journal，
  再允許 node 返回 checkpoint 或輸出事件。啟用 Redis 的即時、resume、approval-resume
  及 Goal worker 路徑使用同一機制。
- 同一交易包含決策、公開事件（若命中或掃描不完整）、audit、finding 與允許的內部觸發。
  既有 Postgres outbox 自動捕獲公開事件／audit／finding，journal 和 HMAC secret 不歸檔。
- 決策識別涵蓋 run／Goal、步驟、attempt、工具輪次、規則與政策、掃描結果及 keyed
  內容識別；掃描原文、未加密的內容 digest、HMAC secret 不寫入 journal／事件／PG。
- stream consumer 只重用已提交的事件 cursor；重送不重複產生 finding／內部觸發，
  不清除已完成的人工 review。錯誤 kind／resource／事件內容不能冒用 journal cursor。
- 寫入前 WATCH 並檢查目的 key 型別，避免 Redis MULTI 不會 rollback WRONGTYPE 的陷阱；
  journal 成功標記最後寫入。儲存錯誤不得授予工具或輸出釋出權。
- commit 前崩潰：node 尚未完成，resume 必須重新執行。commit 後崩潰：診斷已在公開
  stream，不能因 stream consumer 沒收到而遺失。這是至少一次＋去重，不是 exactly-once。

## 驗證中發現並修正的冷啟動競態

- 全新 Redis 下兩個 Gateway 同時建立 checkpointer 索引，確實重現第三方 RedisVL 的
  `Index already exists`，造成其中一個程序退出；既有索引會掩蓋此問題。
- Gateway 與 worker 改用同一 bootstrap 鎖序列化初始化：lease 60 秒，setup 最長 30 秒，
  等待最長 65 秒；只有持有 token 的程序可釋放，逾時／取消會清理 saver。
- 使用另一個全新 Redis 重跑兩副本三個 SIGKILL 時序與中段內容測試，4 項通過；另有
  4 項鎖併發、setup timeout、cancel、不可釋放他人鎖的回歸。
- 主動工作 E2E 初次未抵達 Skill 撤銷的模型呼叫門檻。加入 bootstrap 修補後重跑，
  原有等待期限未延長，已通過撤銷及雙 worker 崩潰恢復。未把首次失敗抹成通過。

## 限制及操作注意

- Redis 持久化、備份與事件保留政策仍決定故障及長期重播範圍；本修改沒有提供零 RPO。
  journal TTL 至少涵蓋 checkpoint TTL 加一小時，以及 finding TTL；公開 stream 仍受既有保留規則限制。
- 未啟用 Redis 的 ephemeral 路徑沒有 durable journal；不得宣稱其可跨程序恢復。
- 程序中斷但尚未產生掃描結果，不能聲稱已偵測到攻擊；恢復後重新掃描。
- 每次掃描啟動隔離程序會增加延遲；舊的 head/tail 與提前 draft streaming benchmark
  不可直接當成本版的 latency profile。完整效能／HA／PITR／真實模型品質屬 M9。
- 完整掃描不是完整威脅偵測：語意繞過、跨事件攻擊與規則誤報仍可能存在。
- M2 的 Agent identity／ACL／audit chain／conversation fencing 與其餘候選功能仍未實作。
